What it is

A Duolingo-shaped piano tutor. You play a real instrument — MIDI keyboard, acoustic piano via microphone, or the on-screen keyboard — and the app scores your performance note by note, adapts what it teaches you next, and wraps the whole thing in collectible cats that evolve as you improve.

The product bet is that the two halves reinforce each other. The signal-processing half — hearing what you actually played and grading it fairly — is what makes it a real teaching tool rather than a quiz app. The retention half — streaks, gems, leagues, evolving cats — is what gets a beginner to day thirty, which is where piano skill actually starts to compound.

The three input methods

These are ranked by fidelity, and the app degrades down the list automatically:

  1. MIDI — exact note, exact velocity, sub-15ms. The ideal case.
  2. Microphone — an ONNX polyphonic model for chords, YIN pitch detection as the monophonic fallback. This is the differentiator: it means someone with an acoustic piano and no MIDI cable can still use the app.
  3. Touch — the on-screen keyboard. Always available, teaches note geography, but can't teach real technique.

Architecture

One rule shapes everything: business logic in src/core/ is pure TypeScript with no React imports. Scoring, curriculum planning, MMR, music theory — none of it can import a hook or touch a component.

That constraint buys three things. The logic is testable without a renderer, which is most of why 3,263 tests run in 42 seconds. It is portable — the planned web version reuses core/ untouched. And it forces a clean seam: if a scoring change needs a React import, the design is wrong.

The critical path

If you only internalise one thing before the interview, make it this: what happens between a finger hitting a key and a score appearing.

Why the split matters

This is the part interviewers tend to push on, so be ready to defend it.

Real-time feedback has to be greedy — when a note lands, you must decide right now which expected note it was, and light up the right key. It searches ±1.5 beats for the nearest unconsumed note and marks it used.

Final scoring cannot be greedy. If you rush the third note, a greedy matcher consumes the fourth note's slot and every subsequent note cascades into being "wrong" — one small error destroys the whole score. So matchNotes() runs once at the end over the complete performance and finds a globally sensible assignment.

The cost is that the on-screen feedback and the final score can disagree slightly on a messy take. That is an accepted trade: a fair score matters more than perfect agreement with a transient overlay.

Timestamp domains

A subtle bug class lives here. Played notes arrive with Date.now() epoch timestamps; the scoring engine expects milliseconds relative to beat zero. useExercisePlayback.handleCompletion converts before scoring: adjusted = Date.now() − startTimeRef − countInMs. Getting this wrong once meant comparing trillion-millisecond values against small relative ones — every note read as infinitely late and every score came out zero.

Audio engine

Two implementations behind one interface, chosen at runtime by createAudioEngine().

EngineMechanismLatencyUsed when
WebAudioEnginereact-native-audio-api over JSI — direct native calls, no bridge serialization<10 msPreferred. Needs the native module.
ExpoAudioEngineexpo-av with round-robin voice pools over real FluidR3 GM piano samples~30 msFallback — Expo Go, or when the JSI module is missing

The factory tries to construct WebAudioEngine inside a try/catch with a lazy require(). If the native module isn't linked, construction throws, and it falls through to Expo. The app never hard-fails on audio.

Round-robin voice pools

The fallback engine's non-obvious trick. Naively, replaying a note means stop-then-play, which races: the stop is async and can land after the new play, cutting off the note you just started. Instead it pre-loads two voice objects per note and alternates. Repeating a note grabs the other voice, so there is always a free one and no stop is needed on the hot path.

It pre-loads C2–C6 at octave spacing and pitch-shifts ±6 semitones via playbackRate — five samples covering the full range at about 132 KB, instead of 88 individual files.

The rule that shapes all of this

Never allocate inside an audio callback. A new Float32Array() per buffer triggers garbage collection mid-stream and you hear it as a click. Every buffer in the pipeline is pre-allocated once and reused. This is the single most important constraint in the audio and input code.

The iOS audio-session trap

Worth knowing because it cost real debugging time. Enabling microphone input switches iOS into PlayAndRecord, which by default routes output to the earpiece — the app goes nearly silent and looks broken. Two separate libraries (expo-av and react-native-audio-api) share one AVAudioSession but keep independent internal state, so whichever configures last wins.

The fix: configure through AudioManager.setAudioSessionOptions() synchronously as the primary path, with expo-av only as fallback, and use measurement mode when recording. Default mode applies voice-processing that is tuned for speech and audibly mangles piano.

Input pipeline

InputManager is a factory and normalizer. Whatever the source, downstream code receives one MidiNoteEvent shape — so the scoring engine has no idea whether a note came from a keyboard, a microphone, or a fingertip.

Microphone: the hard one

Two detection modes:

  • Polyphonic — an ONNX Basic Pitch model, 88 note bins, up to six simultaneous voices. Audio is resampled 44.1 → 22.05 kHz, inferred, then passed through MultiNoteTracker for per-note onset/release hysteresis. This is what lets the app hear a chord.
  • Monophonic — YIN autocorrelation with octave-error correction and a median filter. Cheaper, and the automatic fallback if ONNX fails to load.

Total mic latency is roughly 120 ms. Two compensations make it usable: a fixed −100 to −120 ms offset applied at the InputManager, and a 1.5× timing tolerance multiplier for mic input, because inferred onsets are genuinely fuzzier than a MIDI event and grading them on the same curve would be unfair.

Tuning lesson worth quoting

Early mic tuning was done by playing piano through phone speakers into the mic. That signal is nothing like a real instrument — the thresholds derived from it were badly wrong on an actual piano. Retuning against a real acoustic source moved the RMS gate from 0.006 to 0.002, because measured iPhone RMS for real piano sits at 0.003–0.009. Tune against the real signal, not a convenient proxy.

A related gotcha: iPhones capture at 48 kHz, not the assumed 44.1 kHz. Every detected pitch was sharp by that ratio until AudioCapture started reading the actual rate off the buffer and calling detector.setSampleRate().

Scoring engine

Pure functions in src/core/exercises/. No React, no I/O, heavily tested — this is the most safety-critical logic in the app, because unfair scoring destroys trust faster than any crash.

Five weighted dimensions

DimensionWeightMeasures
Accuracy35%Right notes
Timing30%On the beat, within tolerance windows
Duration15%Held for the written length
Completeness10%Played ÷ expected
Extra notes10%Inverted penalty: 100 × 0.85^extras

The extra-notes penalty is exponential rather than linear on purpose. One stray note is a slip and barely matters; ten stray notes means you were mashing, and the curve should say so.

Timing windows scale with difficulty

Tolerance is per-exercise, not global — a beginner gets ±75 ms for "perfect", an expert ±20 ms. Same algorithm, different constants, so the curve gets genuinely harder as you progress rather than the content merely getting denser.

Per-type strategies

scoreExerciseByType() dispatches to a specialised scorer, with default → scoreExercise. Rhythm exercises are the clearest example: the tap zone emits MIDI note 60 for every tap and pitch matching is skipped entirely, because in a rhythm drill which note you hit is meaningless — only when matters.

Type inventory — be precise here

17 exercise types are defined in types.ts. Six are genuinely implemented end-to-end with dedicated UI and scoring: play, rhythm, earTraining, chordId, sightReading, callResponse — each with its own component (RhythmTapZone, ChordPrompt, ListenPhaseOverlay, SightReadingOverlay, CallResponsePhase). The remaining eleven — quiz and gamified variants like intervalQuiz, chordBuilder, bossBattle — are typed and routed but fall through to play-along. Claim six, not seventeen.

Adaptive curriculum

The pedagogical core, and the most defensible piece of engineering in the project.

The skill DAG

SkillTree.ts holds 120 skill nodes across 18 tiers in 12 categories, wired as a directed acyclic graph of prerequisites. Not a list — a graph, so multiple paths can converge and unlock the same downstream skill.

Skill decay

Mastery is not permanent. Each skill decays on a 14-day half-life; below a 0.5 threshold it re-enters the review pool. This is spaced repetition applied to motor skill, and it is the reason the app can be honest about a user having "learned" something.

Session planning

selectSessionType() picks one of five shapes from current state:

TypeChosen when
review3+ skills have decayed below threshold
mixed1–2 skills decayed — new material plus repair
challengeEvery 5th completed exercise — a deliberate difficulty spike
new-materialDefault when nothing is decaying
endgameAll 120 skills mastered — varied AI-generated sessions
The invariant to state out loud

The daily plan is cached by date and must never regenerate mid-day. Adding masteredSkills as a dependency of plan generation seems reasonable and is catastrophic: completing an exercise mutates mastery, which regenerates the plan, which reshuffles the remaining items under the user mid-session. Plan generation depends on the date and nothing else. This is enforced in DailyPlanManager.ts.

Supporting pieces: WeakSpotDetector finds recurring failure patterns (a specific note, a hand transition, a rhythmic figure) rather than just a low score, and DifficultyEngine nudges tempo +5 BPM per mastered exercise so progression is continuous rather than stepped.

State & persistence

14 Zustand domain stores, split by concern rather than by screen: progressStore (XP, streak, lessons), authStore, catEvolutionStore, gemStore, learnerProfileStore, rankStore, seasonStore, socialStore, guildStore, leagueStore, songStore, settingsStore, achievementStore, exerciseStore.

Two save strategies

createDebouncedSave
500 ms — settings, league standings, routine progress. Coalesces bursts.
createImmediateSave
0 ms — gems, onboarding completion, selected cat. Anything that must survive a navigation or crash on the very next frame.

The distinction came from a real bug: gems earned at the end of an exercise were lost because the user navigated away inside the debounce window. Currency needs a synchronous write; a volume slider does not.

Two patterns that recur everywhere

Always read via getState() inside callbacks. Closures in long-lived callbacks — audio handlers, timers, event subscriptions — capture state at creation. By the time they fire, that state is stale. Reading useStore.getState() at call time gets the current value. This bit the codebase repeatedly, which is why the gameplay hook is built almost entirely out of refs: playedNotesRef, testModeRef, skillIdParamRef.

Never mutate outer variables inside a Zustand updater. set(state => {...}) can be invoked twice under React strict mode. Any side effect inside it double-fires — which, for a gem award, means paying out twice. Read before and after with get() instead.

Cross-device sync

Offline-first. The device is authoritative for the current session; Firestore is the durable merge point. The core loop works with no network at all.

Sign-in order is load-bearing

  1. pullRemoteProgress() — fetch authoritative cloud state first
  2. migrateLocalToCloud() — push local-only data up
  3. pushAllProgressData() — reconcile
  4. startPeriodicSync() — 5-minute flush cycle

Reversing steps 1 and 2 pushes stale local state over good cloud state and silently destroys progress. The ordering is the correctness guarantee.

Merge strategy

Deliberately biased toward never losing user progress: highest wins for numeric values (XP, scores, MMR, gem balance), union for sets (mastered skills, owned cats, unlocked achievements). Twelve data types sync bidirectionally.

Two rules learned the hard way

Every fetch in a Promise.all needs its own .catch(). Without them a single failed request rejects the whole batch and the user loses everything on sign-in. One flaky network call should degrade one data type, not all twelve.

Never call PersistenceManager.clearAll() without first calling pushAllProgressData(). Sign-out clears local storage; if the push hasn't happened, that data is simply gone.

Cost control

Responses are cached on a composite key: exercise ID + score bucket (rounded to 10) + attempt bucket + a hash of the error profile. Roughly 80% hit rate takes projected cost from about $30/month to $6.

Prompt design

The system prompt is constrained hard: two to three short sentences, exactly one improvement area, one specific actionable tip, always end encouraging. It also explicitly forbids contradicting the supplied scoring data — without that, the model cheerfully congratulates a user on a failed attempt. No PII goes into any prompt; only structured score data. Audio never leaves the device.

Voice

ElevenLabs primary with 13 per-cat neural voices, expo-speech as fallback, file-cached to avoid re-synthesising repeated lines. Both are lazily require()d inside functions rather than imported at module top level — a top-level import pulls expo-file-system and expo-av into Jest's module graph and breaks the test run.

Content pipeline

599 exercises across 50 lessons as version-controlled JSON, plus 582 songs in Firestore.

Lazy loading

Requiring 599 JSON files eagerly would balloon the bundle and startup time. ContentLoaderRegistry.generated.ts is code-generated by a script and maps each exercise ID to a () => require(...) thunk — so a file is parsed only when that exercise is actually opened.

A correctness detail worth mentioning

Cat abilities are disabled during mastery tests, guarded by testModeRef. Otherwise a cat that widens timing windows would inflate the very assessment used to decide whether you have mastered a skill — the measurement instrument would be affected by the thing it measures.

Hard problems solved

Interviewers ask for a hard technical problem. These are the strongest four, each with a real root cause and a real fix.

1 · The audio session that silenced the app

Symptom: enabling the microphone made piano audio nearly inaudible.
Root cause: two libraries sharing one AVAudioSession with independent internal state. Mic access forces PlayAndRecord, which routes output to the earpiece.
Fix: a single synchronous configuration path through AudioManager, expo-av demoted to fallback, and measurement mode so iOS stops applying speech-tuned processing to piano.
Lesson: shared global native resources need one owner. Two abstractions over one resource will fight.

2 · Stale closures in the gameplay loop

Symptom: scores computed from partial note data; abilities leaking into test mode.
Root cause: long-lived callbacks capturing state at creation time. Notes appended to a state variable were invisible to the completion handler.
Fix: refs for anything read inside a callback, and getState() for store reads. useExercisePlayback now holds roughly twenty refs — that is the pattern, not an accident.
Lesson: React's render model and real-time event streams have different lifetimes. Refs are the bridge.

3 · The mid-day plan reshuffle

Symptom: the daily practice list changed while the user was working through it.
Root cause: masteredSkills was a dependency of plan generation. Completing an exercise updated mastery, which regenerated the plan.
Fix: cache keyed on date alone, persisted to AsyncStorage, regenerated only on date change or full completion.
Lesson: derived state that a user is actively consuming must be pinned. Reactivity is not always desirable.

4 · Timing that was fair to the microphone

Symptom: mic users scored far worse than MIDI users at identical skill.
Root cause: ~120 ms inherent detection latency graded on the MIDI curve.
Fix: fixed latency compensation plus a 1.5× tolerance multiplier for mic input.
Lesson: when input fidelity differs by channel, the grading curve has to differ too — otherwise you are measuring the hardware, not the player.

Interview drill

The questions this codebase invites, and the answers that hold up. Open each and say it out loud once.

Walk me through what happens when a user plays a note.

Input arrives from one of three sources and InputManager normalizes it into a single MidiNoteEvent, applying per-source latency compensation. From there it splits into two paths on different clocks. Immediately: the audio engine plays the sample over JSI, and a greedy nearest-note match within ±1.5 beats drives the key highlight and the PERFECT/GOOD/LATE overlay — budget under 20 ms, because late feedback feels broken. Deferred: the event is appended to playedNotesRef — a ref, not state, to avoid stale closures. At completion, timestamps are converted from epoch to beat-relative and the whole performance is scored once, globally. That score then fans out to XP, gems, streaks, achievements, cat XP, MMR, and league points, which persist to AsyncStorage and queue for Firestore.

Why two different matching algorithms for feedback and scoring?

Because they optimise for different things. Feedback must be greedy — you have to decide instantly which note was hit to light up a key. Scoring cannot be, because greedy matching cascades: rush one note, and every subsequent note gets assigned to the wrong slot, so one small error tanks the entire score. Deferred global matching over the complete take gives a fair result. The trade-off is that the overlay and the final score can disagree slightly on a messy performance — and I would rather the score be right, because that is what the user's progress depends on.

How do you keep audio glitch-free?

One hard rule: no allocation in audio callbacks. A new Float32Array() per buffer triggers GC mid-stream and you hear it as a click, so every buffer is pre-allocated once and reused. Beyond that, JSI instead of the RN bridge to avoid serialization on the hot path, and round-robin voice pools — two sound objects per note, alternating — so repeating a note never needs an async stop that could race the next play.

Why Zustand and not Redux?

Redux's ceremony doesn't pay for itself at fourteen stores with one developer. But the decisive factor is getState(). A lot of this app runs in long-lived callbacks — audio handlers, timers, MIDI subscriptions — where a closure captures state at creation and is stale by the time it fires. Being able to read current state synchronously at call time, without a subscription or a hook, is exactly what real-time code needs.

How does offline mode work?

Offline-first by design: the device is authoritative for the session, Firestore is the durable merge point. Everything writes to AsyncStorage immediately, with a queue flushed every five minutes when there's a connection. Merges never lose progress — highest-wins for numbers, union for sets. The ordering on sign-in is load-bearing: pull, then migrate, then push. Reversing pull and migrate would push stale local state over good cloud state. And every fetch in the parallel pull has its own catch, so one flaky request degrades one data type instead of wiping the sign-in.

What's the hardest bug you've fixed here?

Enabling the microphone made the app nearly silent. It looked like an audio bug, but the root cause was two libraries — expo-av and react-native-audio-api — sharing one iOS AVAudioSession while keeping independent internal state. Requesting mic access forces PlayAndRecord mode, which routes output to the earpiece. Whichever library configured last won, so the behaviour was inconsistent. The fix was making one library the single owner of session configuration, synchronously, and using measurement mode so iOS stops applying speech-tuned voice processing that audibly mangles piano. The general lesson: a shared global native resource needs exactly one owner.

How do you test something this real-time?

By keeping the real-time part thin. All the logic worth testing — scoring, curriculum, MMR, music theory — lives in src/core/ as pure functions with no React imports, so it tests without a renderer or a device. That's why 3,263 tests run in 42 seconds. The genuinely device-dependent parts, audio latency and mic accuracy, can't be meaningfully unit-tested, so those are verified by hand on hardware — and I'm explicit that that verification is still incomplete for some paths.

What would you refactor first?

ExercisePlayer.tsx at 3,811 lines. It grew organically as each exercise type was added and now branches on type in too many places. I'd decompose it into per-type controllers behind a shared interface, mirroring how scoreExerciseByType already dispatches on the scoring side — the seam exists in the core, it just hasn't been pulled through to the UI. That refactor is also the natural place to finish the eleven exercise types that currently fall back to play-along.

How do you keep AI costs and reliability under control?

Three layers. Caching on a composite key — exercise, score bucket, attempt bucket, error-profile hash — gets roughly 80% hit rate, taking projected cost from about $30/month to $6. Every AI path has a deterministic fallback, so the app is fully usable with AI switched off; coaching just gets less personal. And all Gemini calls go through Cloud Functions, so the key never ships in the client bundle. On privacy: no PII in prompts, only structured score data, and audio never leaves the device.

What's the weakest part of this codebase?

Accessibility. There are eight P0 issues, mostly missing labels on interactive elements across most screens, and it's the one gap that's both a shipping blocker and a genuine user-facing quality problem. It's what I'd fix first with dedicated time. Second is that end-to-end coverage is scaffolded but not real — all my actual confidence comes from unit and integration tests, and I'd rather be honest about that than overstate it.
